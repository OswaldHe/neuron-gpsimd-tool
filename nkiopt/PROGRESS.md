# nkiopt progress log (GPSIMD custom ops vs pure NKI)

Method: `bench.py <case> [--set K=V]` builds baseline_kernel (pure NKI) and gpsimd_kernel (gp.call), runs both
through toolchain/bin/gpsimd-run (same runner; GPSIMD run checks per-core receipts), profiles the last of N warm
executions with nrt_profile_start/stop and reads total_exec_time with `neuron-explorer view --output-format
summary-json`. Results in cases/<case>/build*/results.json.

Calibration: GPSIMD clock 1.2 GHz (1M-cycle spin = 833 us); one GPSIMD call costs ~2.6 us more than one
NKI tensor_copy (cases/overhead: 3.63 vs 6.24 us). Local DataRAM: load-use 6 cycles, independent loads
pipeline to 2; SBUF posted store 19 cycles but ~80 when 8 cores store into the same partition (spread
destinations over partitions). Barrier now polls flags with one iDMA (was 8 blocking SBUF loads): ~1 K cycles.

## MoE EP dispatch demo (cases/moe_ep_dispatch)

Pipeline per rank before the all-to-all: nkilib rmsnorm_router_topk_a2av -> permute_routed_tokens ->
build_all2all_dispatch_metadata (R = E, one expert per rank, so send-buffer rows match the metadata).
Three versions: nkilib as shipped, GPSIMD (all routing math in one call `moe_dispatch`), and a
hand-optimized pure-NKI routing (BASE=opt: key = e*N + s, dest = #smaller keys via tensor_scalar_reduce on
[128,128], one-hot permutation matmul for token/affinity, one-hot matmul + min + matmul + scan for metadata).
Timing references: BASE=router (router alone), BASE=floor (router + gather/pack/store, routing = constants).

| us (median of 5) | Qwen3-235B T=16 K=8 E=128 | Mixtral T=32 K=2 E=8 |
|---|---:|---:|
| router | 19.9 | 17.2 |
| floor | 22.6 | 27.4 |
| nkilib | 194.7 | 48.1 |
| GPSIMD | 39.3 (4.95x vs nkilib) | 39.0 (1.23x) |
| NKI-opt | 37.0 | 36.2 |

All bit-exact. Conclusion: at decode size (T*K <= 128 slots in one tile) a well-written pure NKI version is
as fast as (slightly faster than) GPSIMD; the GPSIMD speedups for moe_permute / moe_dispatch_meta /
moe_ep_dispatch are over nkilib's implementations only.
GPSIMD op tuning log (cycles per core): single core 20K -> all cores sort, split rows 17K (division was not
the cost: quou exists; nsau exists) -> compile-time T/K, overlapped fetch, metadata built locally + one iDMA
(8 cores storing into the same 4 partitions serialize at ~80 cycles/store), metadata from the sort's
histogram when R = E: ~7K (fetch 1K, count+prefix 2.3K, scatter scan 2.7-3.4K, meta 0.8K, drain 0.35K).
Posted stores vs iDMA for 16 small rows per core: same time; the cost is the scalar scan (~20 cycles/slot).

Toolchain fix: gpsimd-neff inject now puts the KERNEL_CALL at the site's first output (join) marker instead
of the last marker. NKI scheduled the indirect DMA's descriptor generation (Pool op 0xd4, reading output 0)
between two output markers, which made the injection impossible ("would come later").

## MoE EP layer end to end (cases/moe_ep_layer)

Whole MoE layer of one EP rank in one NEFF (Qwen3-235B: T=16 K=8 E=128 EP=128, I=1536, bf16 weights):
nkilib router -> dispatch (version-specific) -> loopback all-to-all -> nkilib moe_tkg (all-expert, 1 local
expert, POST_SCALE) -> loopback back -> combine (one-hot matmul) + residual. Collectives not run. Output
checked against numpy (rel L2 3.8e-3), dispatch outputs exact.

| median total_exec_time | us |
|---|---:|
| nkilib, loopback copy waits for the metadata (as a real all-to-all must) | 476.6 |
| nkilib, loopback copy depends on the send buffer only (wrong: metadata hides behind the expert FFN) | 373.4 |
| GPSIMD, loopback depends on the send buffer only (metadata comes out of the same call) | 307.0 |

The expert FFN dominates (PE busy 209 us). Making the copy wait for the metadata needs a runtime loop on Pool
(register + fori_loop), which gpsimd-neff inject rejects ("Pool program contains control flow"), so the GPSIMD
layer was not re-measured with that loopback. Additive estimate: 39.3 (dispatch step) + 281.9 (476.6 - 194.7,
downstream of nkilib's dispatch) = 321 us. End to end vs nkilib: 1.48x (estimate, same loopback) to 1.55x
(measured, simpler loopback). Against the hand-optimized NKI dispatch (37.0 vs 39.3 us) GPSIMD would be ~2 us
slower in a ~320 us layer (~0.99x); stopped there (user: no further work if GPSIMD is slower).

## DeepSeek-V4.1-Flash demos (cases/ds41_*) vs the port's hand-optimized NKI

Baseline code: vllm-neuron branch deepseek_v41_trn3 @ 3b74533, contrib/models/deepseek_v41/src/kernels/tp64
(clone in ../ext/vllm-neuron; unmodified copies of the helper modules in cases/ds41_*/ds41{k,d,s}/). One
NeuronCore (the deployment's LNC=2 split halves every part), collectives not run.

Toolchain: gpsimd-neff inject now supports NKI dynamic control flow (nl.fori_loop with register trip counts) when
every gp.call precedes the Pool program's first block boundary: blocks end with drain / barrier / semaphore
reset (op 0xB0), so waits are renumbered only before each engine's first reset; branches use label ids
(0xA9 -> 0xCC), the unconditional jump 0xDD has an absolute target (byte 16) that is relocated. cases/cf_loop
checks it; run_examples.sh 19/19 PASS.

Measured costs that shape the designs: one fori_loop iteration ~2.4 us (cf_loop, 1 vs 201 iterations:
13.0 / 495.7 us); a software-DGE indirect row gather ~5.5 ns per index entry whether the entry is valid or
skipped (oob_mode.skip; dma_skip: 64 x 640-row gathers 224 us at 100 % / 25 % / 0 % valid).

Engram read-out (ds41_engram; port: engram_gather + mk_mx.gemm_rows + engram_gate_tile). GPSIMD compacts the
rank's hits (a 6.0M-row shard overlaps <= 2 of the 24 ~16M-row hash columns: ~0.375 of 24 lookups a token);
NKI zero-fills emb and gathers / scatters only those rows. Schedule: runtime fori_loop over the hit count at
prefill sizes; NCH = 2*Tp/128 static DMAs (padding skipped) at decode, because the loop's block boundary
drains every engine and costs the overlap of the gather with the GEMM's weight stream (T=60 dynamic: 0.98x).

|---|---:|---:|---:|---:|---:|---:|
| 1024 (prefill) | 3362.9 | 2968.9 | 1.13x | 506.9 | 102.4 | 4.95x |
| 2048 (prefill) | 6766.4 | 5926.4 | 1.14x | 980.5 | 200.7 | 4.89x |
| 60 (decode bs10, static) | 697.1 | 681.0 | 1.02x | 62.1 | 24.7 | 2.51x |

Outputs bit-identical to the port's; emb exact vs numpy; GEMM checked against a numpy MX emulation
(rel 0.17 %; the first 8.6 % mismatch was my test data: the engram term was below the stream's bf16 ulp).

Engram n-gram hashing (ds41_ngram; port: step_kernel._hash_rows). NKI keeps the window gathers (token map,
history through the block table); one GPSIMD call does MULL/MULUH products, XOR and a 64-bit Barrett
reduction (mu = floor(2^64/p) from the host, <= 3 corrections) for the 48 columns. Iterations: per-element
5-step 32-bit Barrett 93.8 us (0.93x) -> column-major + only the T real rows 62.2 -> 64-bit Barrett 48.5.

| size | NKI | GPSIMD | |
|---|---:|---:|---:|

| prefill T=1024 | 531.1 | 449.7 | 1.18x |
| prefill T=2048 | 1055.6 | 890.6 | 1.19x |

Explored, not a win: MoE decode (routed_experts: 56.5 us fixed + ~84 us per active expert of MXFP4 weight
streaming; one GPSIMD-scheduled loop would make the weight addresses dynamic and lose the hardware DGE);
prefill attention key dedup (steps are DGE-paced, 5120 rows a step, but dedup needs dynamic sizes: skipped
entries cost the same and loops cost 2.4 us an iteration); decode attention slot lookups (nc_n_gather path is
already a GPSIMD built-in); mHC / DSpark (floating point; no FPU on the cores).
