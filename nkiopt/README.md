# nkiopt: GPSIMD custom operators vs pure NKI on trn3

Where does a custom GPSIMD operator (toolchain in `../toolchain`: C++ for the 8 GPSIMD cores, injected into
the NKI-compiled NEFF as a KERNEL_CALL) beat the best pure-NKI formulation, measured end to end on the
device? Every case here has a **pure-NKI baseline** (an nkilib kernel as shipped, or the best NKI version
we could write) and a **GPSIMD version** that replaces exactly the part NKI is bad at; both run through
the same runner, and the GPSIMD run verifies per-core receipts (the work provably ran on the GPSIMD cores).

## Results (trn3, one NeuronCore, LNC=1)

`total_exec_time` from a device profile: the runner executes the NEFF N=5 times and profiles the last
(warm) execution with `nrt_profile_start/stop`; `neuron-explorer view --output-format summary-json` reads
`total_exec_time` from the NTFF. Median of 3-5 captures (spread < 1%).

Calibration (`overhead`, `clock`, `memlat`): one GPSIMD call costs ~2.6 us more than one NKI tensor_copy;
GPSIMD clock 1.2 GHz; local RAM load-use 6 cycles (independent loads pipeline to 2); posted SBUF store
19 cycles (~80 when 8 cores hit the same partition); soft-float add ~120 cycles.

## What makes a GPSIMD win (and what does not)

The GPSIMD custom path is 8 scalar base-ISA cores (no vector TIE, soft-float). It wins where NKI needs
**many dependent instructions or descriptor-generated DMAs for a small amount of integer work**:

* **Sorting / grouping** (`argsort`, `moe_permute`): NKI has no sort; nkilib sorts with N/8 sequential
  `max8` + `nc_match_replace8` passes over the row (O(N^2), 2N/8 dependent instructions). A parallel LSD
  radix sort on the GPSIMD cores is O(N) and skips constant digits (expert ids: 1-2 passes).
* **Tiny control-heavy metadata** (`moe_dispatch_meta`): nkilib unrolls ~12 dependent Vector/Scalar/PE
  instructions per destination rank; one GPSIMD call does a per-token bitset, counts and a scan.
* **Sparse accumulation with irregular addresses** (`bm25`, `scatter_add`): in NKI every indirect DMA is
  SW DGE (descriptors generated by the Pool engine): ~6.8 us per 128 indices for `dma_compute`
  read-modify-write, and duplicates force nkilib's `scatter_add` to process 128-row tiles strictly in
  sequence (gather, equality-matrix matmul, add, scatter). On the GPSIMD cores the postings / indices are
  streamed with the iDMA and accumulated in local RAM, each core owning a destination range.

It does **not** win on:

* **Dense math** (the GDN/SSM kernels of `neuron-neff-doc/experiments`: `gdn_cte`, `gdn_tkg`,
  `gdn_block_tkg`, `selective_scan`, `ssd`): they contain no index math, gathers or data-dependent
  control; PE/ACT/DVE process 128 lanes per cycle while a GPSIMD core spends ~100-300 cycles per fp32
  soft-float op. Same for dense quantization/dequantization (DVE: 128 elements/cycle).
* **Table lookups NKI already vectorizes** (`prior_index`): nkilib broadcasts the block table and uses
  `nc_n_gather` (a GPSIMD built-in); our scalar lookup (~14 cycles/key on 8 cores) only matches it.
* **Graph ANN at this scale** (`ann`): per expansion one 640 B iDMA + 32 PQ distances (~7 K cycles per hop
  per core); exact brute force on PE streams 512K x 128 int8 in 657 us for 8 queries with recall 1.0,
  while the beam search (L=64) takes 741 us at recall 0.36 (PQ with 16 subspaces cannot separate the
  close neighbours; exact-distance search over the same graph reaches recall 1.0 in ~80 hops but would
  need random 128 B vector reads per neighbour). Graph search would pay off only for much larger N
  (>~10M) and low batch, which needs more than the 512 MB GPSIMD HBM window used here.
* Problems too small to amortize the ~2.6 us call (`argsort` N=128).
* **Decode-size MoE routing against a hand-optimized NKI version** (`moe_ep_dispatch`, see below): with
  T*K <= 128 routed slots everything fits one 128x128 tile, so pure NKI can rank the slots by comparison
  (`tensor_scalar_reduce` on [128, 128]), move them with a one-hot matmul and count ranks with a matmul and
  a scan, in about 20 instructions. That is as fast as the GPSIMD call. The gains of `moe_permute`,
  `moe_dispatch_meta` and `moe_ep_dispatch` are therefore gains over nkilib's current implementation
  (argsort by N/8 max8 passes, per-rank unrolled metadata, SW-DGE gathers), not over the best NKI.

## MoE dispatch demo (`cases/moe_ep_dispatch`)

What one rank of an expert-parallel MoE layer runs per decode step before the all-to-all, with nkilib's
a2a-v MoE kernels: `rmsnorm_router_topk_a2av` (RMSNorm + router + top-K + softmax) ->
`permute_routed_tokens` (send buffer: [T*K, H+3] rows `[hidden, affinity, token]` grouped by expert) ->
`build_all2all_dispatch_metadata` (send counts / displacements per rank). One expert per rank (R = E), so
the send buffer's per-rank row counts equal the metadata. The all-to-all itself (a collective) is not run.
Every version is checked against numpy: router outputs within bf16 tolerance, send buffer and metadata
exact from the device's own routing results.

| (median total_exec_time, us) | Qwen3-235B (T=16 K=8 E=128 R=128) | Mixtral-8x7B (T=32 K=2 E=8 R=8) |
|---|---:|---:|
| router alone (`BASE=router`) | 19.9 | 17.2 |
| floor: router + gather/pack/store, routing math = constants (`BASE=floor`) | 22.6 | 27.4 |
| nkilib as shipped | 194.7 (routing math +172.1) | 48.1 (+20.7) |
| GPSIMD: routing math in one call (`moe_dispatch`, 8 cores) | 39.3 (+16.7) | 39.0 (+11.6) |
| hand-optimized pure NKI (`BASE=opt`) | **37.0** (+14.4) | **36.2** (+8.8) |

The GPSIMD call is ~7K cycles per core (fetch 1K, counting sort 2.3K, row scatter 2.7-3.4K, metadata 0.8K)
plus the ~2.6 us call: the scalar cores are not faster than ~20 NKI instructions on a single tile.

### End to end: the whole MoE layer (`cases/moe_ep_layer`)

The same rank, whole layer: router -> dispatch -> (all-to-all) -> nkilib `moe_tkg` expert FFN (one local
expert, bf16 weights, I=1536) -> (all-to-all back) -> combine + residual, in one NEFF; the collectives are a
local loopback (not run). Output checked against numpy.

| Qwen3-235B, one EP rank (us) | layer |
|---|---:|
| nkilib as shipped | 476.6 |
| GPSIMD dispatch | 307.0 measured / ~321 estimated with the same loopback |
| speedup | **1.48-1.55x** |

The expert FFN dominates (PE busy ~209 us), so the 4.95x of the dispatch step becomes ~1.5x for the layer
(collectives would dilute it further). Against the hand-optimized NKI dispatch, GPSIMD stays ~2 us slower
(~0.99x). The GPSIMD layer could not be re-measured with the metadata-waiting loopback, because that loop puts
control flow in the Pool program, which `gpsimd-neff inject` does not support (details in PROGRESS.md).

## DeepSeek-V4.1-Flash: GPSIMD inside the port's hand-optimized NKI (`cases/ds41_*`)

Baseline = the hand-optimized NKI megakernel code of the vllm-neuron DeepSeek-V4.1-Flash port (branch
`deepseek_v41_trn3` @ 3b74533, `contrib/models/deepseek_v41/src/kernels/tp64`), unmodified copies of its helper
modules in each case (`ds41k/`, `ds41s/`, `ds41d/`). Each demo runs a whole module computation on one
NeuronCore; the GPSIMD version changes only the part named below and keeps the port's code for the rest.
(The deployment splits rows / GEMM columns over the two cores of a logical core, which halves every part;
collectives are not run.) `total_exec_time` medians of 5 profiled executions.

| demo | size | port's NKI | GPSIMD + NKI | speedup | GPSIMD does / NKI does |
|---|---|---:|---:|---:|---|
| **Engram read-out** (`ds41_engram`) | prefill chunk, T=1024 | 3362.9 us | 2968.9 us | **1.13x** | compacts the rank's table lookups / gathers + scatters only those rows, fp8 MX GEMM 6144 -> 25600, gate |
| | its gather stage alone | 506.9 us | 102.4 us | **4.95x** | |
| | prefill chunk, T=2048 | 6766.4 us | 5926.4 us | **1.14x** | |
| | its gather stage alone | 980.5 us | 200.7 us | **4.89x** | |
| | decode bs10, T=60 | 697.1 us | 681.0 us | 1.02x | (static DMA schedule, see below) |
| | its gather stage alone | 62.1 us | 24.7 us | **2.51x** | |
| **Engram n-gram hashing** (`ds41_ngram`) | decode bs10, T=60 | 86.95 us | 48.45 us | **1.79x** | 64-bit products, XOR, mod 48 primes / the n-gram window gathers (token map, history through the block table) |
| | prefill chunk, T=1024 | 531.1 us | 449.7 us | **1.18x** | |
| | prefill chunk, T=2048 | 1055.6 us | 890.6 us | **1.19x** | |

All outputs bit-exact: the read-out's output is bit-identical to the port's (and `emb` exact against numpy, the
GEMM within 0.2 % of a numpy MX emulation); the hashes equal an exact Python-integer `NgramHashState`.

**Why GPSIMD helps**

* *Engram gather = a sparse lookup with a data-dependent hit list.* The 384M-row n-gram table is sharded by row
  over the 64 ranks (6.0M rows, 3.1 GB a rank) and the hash puts each of a token's 24 lookups in its own ~16M-row
  column range, so a shard overlaps at most two columns: ~0.375 of the 24 lookups a token are this rank's (1.5 %).
  The port gathers all T x 24 rows (one indirect DMA per 128 rows and column; every index costs ~5.5 ns of
  software descriptor generation, valid or not) and masks the other 98.5 %. One GPSIMD call scans the ids and
  emits only the hits as (table row, emb row) lists; NKI then issues 3 gathers instead of 192 (T=1024). This is
  stream compaction across a whole index matrix, which the NKI engines have no instruction for (their
  `nonzero_with_count` is per partition row and would need the ids re-laid out and a second indirect gather).
* *Hashing = 64-bit integer arithmetic.* The NKI engines are 32-bit and their int arithmetic is exact only in
  limited forms, so the port builds the products from a [99092, 16] table by indirect DMA and reduces each
  63-bit value with Horner's rule over 7-bit chunks, the quotient from an fp32 estimate corrected by one:
  ~250 dependent Pool instructions per 128-row tile. The GPSIMD cores have MULL / MULUH, so each value takes
  6 multiplies and <= 3 corrections in registers (64-bit Barrett). At decode the NKI chain runs on a 60-row
  tile and is latency-bound (1.79x); on full 128-row prefill tiles the vector instructions amortize (1.2x).

**Why the module gains are smaller than the stage gains.** The read-out is dominated by the dense fp8 `wkv` GEMM
(~85 % at T=1024; at decode its 157 MB weight stream) and the gate, which stay on the tensor / vector engines.
At decode the GPSIMD gather must not use a runtime loop: a `fori_loop`'s block boundary drains every engine
(~2.4 us an iteration, `cases/cf_loop`) and serialized the gather with the GEMM's weight stream (0.98x); the
static schedule (2*Tp/128 DMAs with skipped padding: a token has at most 2 hits) keeps the overlap (1.02x).

**Explored, not a win (measured or by construction)**

* *Prefill sparse attention:* each 8-token step is paced by software-DGE descriptor generation (5120 key rows,
  ~28 us); the 8 tokens share most keys (window: 135 unique rows of 1024; top-k: data dependent), but using that
  needs data-dependent sizes, and NKI has none that are cheap: skipped DMA indices cost as much as real ones
  (`cases/dma_skip`), a loop iteration ~2.4 us, and union-space attention at a static worst-case width makes
  the softmax 6.8x wider.
* *MoE at decode:* 56.5 us fixed + ~84 us per active expert, which is MXFP4 weight streaming; a GPSIMD-built
  schedule would only remove per-expert loop overhead and would turn the weights' static (hardware-DGE)
  addresses into runtime ones.
* *mHC (Sinkhorn), DSpark drafter:* floating point (the cores have no FPU: soft-float 100-300 cycles an op) or
  dense matmuls / argmax that the NKI engines already do natively.

## Layout

```
bench.py                 build both versions, run, verify, profile (total_exec_time), write results.json
cases/<case>/case.py     baseline_kernel, gpsimd_kernel, make_inputs, reference, check, OPS/CFLAGS/HBM
cases/<case>/op.cpp      the GPSIMD operator
cases/<case>/build*/     NEFFs, operator library, inputs, results.json (per configuration)
cases/ann/prep.py        dataset, proximity graph, PQ (cached in cases/ann/data/)
PROGRESS.md              log of the measurements and findings
```

## Reproduce

```bash
source /opt/aws_neuronx_venv_torch_neuronx_2_14_0/bin/activate
cd ~/trn3-gpsimd-re/nkiopt
python bench.py cases/argsort --set N=4096                      # baseline + GPSIMD, 5 profiled repeats
python bench.py cases/argsort --set N=4096 --set KEYS=random
python bench.py cases/moe_permute
python bench.py cases/moe_dispatch_meta --set R=64
python bench.py cases/scatter_add
python bench.py cases/bm25 --set QDF=10000,300000 --tag q10000
python cases/ann/prep.py && python bench.py cases/ann            # ~1 min data prep
python bench.py cases/prior_index
python bench.py cases/moe_ep_dispatch                            # nkilib vs GPSIMD (Qwen3-235B size)
python bench.py cases/moe_ep_dispatch --only baseline --set BASE=opt --tag opt     # hand-optimized NKI
python bench.py cases/moe_ep_dispatch --set T=32 --set K=2 --set E=8 --tag mixtral_nkilib
python bench.py cases/moe_ep_layer --only baseline                 # whole MoE layer, nkilib (476.6 us)
python bench.py cases/ds41_engram --set T=1024 --tag t1024        # DeepSeek-V4.1 Engram read-out (3.1 GB table input)
python bench.py cases/ds41_engram --set T=60 --tag t60            # decode size (static gather schedule)
python bench.py cases/ds41_engram --set STAGE=gather --tag gather # the gather stage alone
python bench.py cases/ds41_ngram --set B=10 --set L=6 --tag dec   # n-gram hashing, decode bs10 (B=1 L=2048: prefill)
```
Options: `--repeats R --iters N --only baseline|gpsimd --no-build --set KEY=VAL --tag NAME`.
